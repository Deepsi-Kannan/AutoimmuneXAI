## Resource measurements and limits

Windows 64-bit, Python 3.11.9, existing environment, one Uvicorn worker,
sequential synthetic requests, approximately 10 ms sampling of the server process
tree (virtual-environment launcher plus actual Python server).

| Measurement | Result |
| --- | --- |
| Process start to successful health response | 6.877 s |
| Startup resident memory | 199.97 MiB |
| Startup sampled peak resident memory | 209.23 MiB |
| Overall OS-reported resident peak, summed across server processes | 249.25 MiB |
| Overall sampled private committed peak | 912.48 MiB |
| First prediction HTTP round trip | 122.3 ms |
| Subsequent predictions | 26.7 / 25.8 ms |
| Explanation requests (prediction + SHAP + HTTP) | 534.4 / 493.7 / 551.1 ms |
| What-if requests | 70.3 / 64.2 / 65.4 ms |
| Prediction sampled resident peak | 202.17 MiB |
| Explanation sampled resident peak | 249.10 MiB |
| What-if sampled resident peak | 225.38 MiB |

RSS is physical resident memory; Windows private commit is a different quantity
and cannot be equated to Linux container RSS. The much higher private commit
requires investigation. These are NOT measurements inside a 512 MB Linux cgroup.
Cold starts on hosted free CPUs can be slower. Concurrent requests and diverse
inputs have not been load-tested. Render Free is a candidate, not certified safe.

The first sandboxed server attempt timed out without startup logs, and the
sandboxed pytest attempt stalled. Tests and valid measurements were rerun outside
the sandbox. An initial probe incorrectly measured only the launcher; its figures
were discarded and replaced with process-tree measurements.

No Docker executable is available and WSL is not installed. No Linux runtime,
container build, cgroup memory-limit test, or Vercel deployment build was run.

## Vercel backend estimate

`scripts/estimate_linux_bundle.py` reads public PyPI metadata and ZIP central
directories via HTTP ranges without installing packages. CPython 3.12 Linux
x86_64 CPU-only wheel contents total **469,488,563 bytes** for NumPy, pandas,
SciPy, scikit-learn, SHAP, Numba, llvmlite and xgboost-cpu. The model adds
2,874,954 bytes. Remaining dependencies, framework code, generated bytecode and
Vercel packaging are additional. This is a partial estimate, not a built bundle.
The individual wheel sizes are recorded in `linux-bundle-estimate.json`.

Standard Linux xgboost 2.1.4 has a modern manylinux wheel of 223,642,416 bytes
compressed, and depends on NVIDIA NCCL on Linux x86_64. The queried current NCCL
wheel is 336,541,086 bytes compressed. That combination already exceeds 500 MB
before extraction and the rest of the stack. The modern Linux deployment should
not use the current standard XGBoost dependency set for Vercel.

xgboost-cpu 2.1.4 is much smaller (14,140,720 uncompressed bytes in its Linux
wheel), but has NOT been substituted or behavior-verified. It must be tested in
an isolated environment against all baseline outputs before any adoption.
CPU-only packaging alone does not establish that the whole bundle fits.

  Phase 3 removes previously tracked bytecode from the Git snapshot while keeping
  local files. Bytecode is also excluded from Docker context.

## Remaining gates

1. Review the isolated clean Windows installation and baseline verification.
2. Build the prepared Docker image on a Linux-capable machine, verify dependency
   installation and rerun the exact baseline checks.
3. Run under a 512 MB memory limit; measure startup, SHAP and concurrent requests.
4. If Render fails that gate, investigate a CPU-only package environment and
   measure it without changing the model or removing features.
5. Only then choose the backend host and approve pushing/deployment.
6. Verify all current UI files are present in the Git change set.
7. Set final HTTPS origins and rebuild the frontend.
8. Compare deployed outputs and cold-start behavior before calling it ready.

No free backend is guaranteed by the current evidence. Vercel frontend + Render
Free backend remains the first candidate, contingent on Linux memory validation.

## Repeating checks locally

From the application directory, using an environment with the runtime dependencies
and `requirements-dev.txt` installed:

```powershell
$env:ALLOWED_ORIGINS = 'https://deployment-check.example'
python -B scripts/verify_deployment_baseline.py
Remove-Item Env:ALLOWED_ORIGINS
python -B -m pytest tests -q -p no:cacheprovider
python -B scripts/measure_backend.py
python -B scripts/estimate_linux_bundle.py
```

The scripts save temporary logs/results under ignored `.deployment-checks/`.
The checked-in baseline is not overwritten by the measurement script.
